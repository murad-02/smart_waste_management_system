Abstract
Solid waste management in Bangladesh faces persistent operational gaps: missed collections, unsegregated waste streams, and limited visibility into the categories and volumes of waste generated by a facility on any given day. Manual logging is slow, error-prone, and difficult to audit. The Smart Waste Management System, abbreviated as SWMS, is a Windows desktop application built to address these gaps at the facility level. The system records every detection event in a structured database, enforces role-based access for administrators, supervisors, and operators, and gives each role a workspace tuned to the actions they are allowed to perform.
The work documented in this report covers the full software engineering lifecycle for the desktop application shell. Requirements were gathered from the project supervisor, from a review of similar systems in the literature, and from the practical needs of a small recycling operation. The system was designed using activity diagrams, swimlane diagrams, sequence diagrams, CRC cards, and a class diagram. Risks were identified and tracked using an RMMM plan, the schedule was estimated using function points, and costs were summed across personnel, hardware, software, and other categories. The implementation uses Python 3.10 with PyQt5 for the user interface, SQLAlchemy on SQLite for persistence, bcrypt for password hashing, Matplotlib for embedded charts, and ReportLab for PDF generation. A placeholder detection engine was implemented so the application can be tested end-to-end before the YOLOv8 model is integrated in a later phase. The placeholder produces realistic category labels, confidence scores, and bin-fill levels, and writes annotated result images to disk.
Six representative test cases were executed against the build, covering authentication, mock detection, history filtering, alert triggering, report generation, and user management. All cases passed against their expected results. The remaining work, namely the integration of a trained computer vision model, a live camera feed, and scheduled reporting, has been deferred to a follow-up phase and is described in the limitations and future work sections. The deliverable is a stable, well-structured application that gives a small waste management operation a usable digital record from day one and a clear path to automated detection later.

Chapter 1.Introduction
1.1 Introduction 
One of the most challenging everyday tasks of small and medium-sized recycling entrepreneurs in Bangladesh is solid waste handling. Waste is delivered in a mixed stream, is segregated by hand, and the quantity of waste received at a site by day of the category of waste is typically recorded on paper or in a spreadsheet that is not accessed at the end of the shift. This practicum was done to look at the recordkeeping and supervision aspect of that problem and implement it with an application that an operator can use offline, a supervisor can audit, and an administrator can set up for the site's waste categories. The application has been named the Smart Waste Management System (SWMS) and is the subject of the rest of this report. This is a modified shell, with a stubbed detection engine, for use on a desktop. The detection engine generates realistic results by adding a training model of YOLOv8 in the following stages of the project.
1.2 Background of the Study 
The Department of Environment estimates that Bangladesh produces over two thousand tons of MSW daily, of which a significant proportion is collected by small private operators who sort the waste at their own premises and sell it to industrial recyclers. Typically, these operators do not have digital tooling. The supervisor will be walking through the sorting area with a notebook in hand, and will record the approximate number of waste bins containing each of the waste categories, then report this to the Office at the end of the day. This presents three operational issues that frequently arose in my discussions with the people I talked to when I was scoping out the practicum. The first one is delayed visibility. The number of plastic items or e-waste is recorded in spreadsheets at the end of the shift, meaning the supervisors only find out about an unusual amount of plastic waste or e-waste several hours after the incident. This time, the Bins are emptied, and the evidence is gone. The second problem is that an audit trail is lacking. If a customer challenges the weight or the category of a delivered batch, there's no simple way for the operator to get the record, as the paper log is stored in chronological order, not by customer or category. The third problem is alerting. Bins are not emptied, or even partially emptied, and only when there is a smell and/or the spillage is visible. No rule-based system exists that says, "if you have more than 30 plastic detections in a day, send an email to the supervisor." Similar gaps in waste management informatics are identified in the literature, as summarized by Rahman et al. (2022) and by the World Bank’s Waste 2.0 dataset, and the same low-cost approach towards creating digital records of waste, with structured alerts, is recommended as a starting point in the same way. Those three problems were the basis for the Smart Waste Management System to be scoped. The system has been designed as a desktop form factor to run on the low-cost Windows computers, which are prevalent in the office back room in Dhaka. The system is not reliant on the internet, as the local SQLite database is used. The development of a place-holding detection engine was created first, since the remaining components of the application – the application's screens, the alert engine, the report generator, and the user management-can be developed, tested, and demonstrated before the model. With the model ready, only one file in the codebase changes.
1.3 Methodology
 Data for this practicum were collected from two types of data sources. They are detailed below. 
1.3.1 Primary Sources.
The following methods were used to gather primary information: 
Weekly meetings with the practicum supervisor for the purpose of agreeing on the scope of each phase and reviewing deliverables with the build document.
Informal discussion with the manager of one of the recycling collection points in Uttara on his daily operations, the types of waste that are usually collected, and the reasons for using paper logs.

Testing of all screens and all workflows was performed hands-on during development, recording the notes in a development journal, which was reviewed at the end of each phase. 
1.3.2 Secondary Sources.
The following were used as secondary sources of information: 
Waste classification based on deep learning has been studied in academic papers, such as Yang and Thung (2017) for the TrashNet dataset, and more recent research for the detection of waste using the YOLO deep learning framework (Adedeji and Wang, 2019).
Government and inter-agency data, such as the World Bank What a Waste 2.0 dataset, and the Department of Environment 2021 status report.
Official documentation for PyQt5, SQLAlchemy, ReportLab, and Matplotlib, used to guide implementation choices.
Public blog posts about bcrypt password hashing and about PyQt threading patterns. 
1.4 Objectives 
The goals of the proposed system are divided into a single general objective and a list of specific objectives that are derived from the general objective and provide the specific measurable deliverables.
1.4.1 Broad Objective
The general goal of the practicum is to create a stable desktop application that will record, classify, and audit the events of waste detection in a small recycling facility, will generate periodic PDF reports for the management to review, and will provide automatic notifications when waste is detected, exceeding the thresholds set by the management, where a clean interface will be provided. 
1.4.2 Specific Objective.
Below are the specific goals of the project:
Create a relational schema in SQLite using SQLAlchemy ORM to store users, detections, alert rules, alerts, activity logs, reports, and application settings.
Create three roles (administrator, supervisor, operator) and define role rules on all screens of the application.
Create a prototype detection engine to generate plausible category names, confidence values, bin-filling values, and to store images with annotations.
Create a dashboard, detection screen, history screen (filter and export), alerts screen, reports screen, users screen for admin, and settings screen (SMTP settings).
Create PDF reports using ReportLab with summary statistics, matplotlib plots and a paginated detections table.
Offer an alert engine that works with the configured thresholds to send email notifications via the configured SMTP server from the detection log.
1.5 Process Model
The iterative-incremental process model was chosen for the practicum. There's enough to the system that if we had to do the waterfall run, we wouldn't risk delaying any integration till the end, and it's small enough that we'd be better off using a separate team in a heavyweight Scrum. The iterative-incremental model is a suitable model because the supervisor can attempt to judge the working increment at the end of each phase before moving on to the next. The phases used: Foundation, Core Logic, UI Widgets, UI Screens, Entry Point, Integration, and Polish (As described in the build document). The process of each iteration was the same, using the same internal review cycle of analysis, design, implementation, and verification, with a review at the interface between iterations.
Below are reasons why this model was chosen:
It brings integration issues to the forefront with each phase yielding a working system, and the database, the engines, and the UI are all tested at the same time from an early stage of the project.
It fits scope changes within a phase without disrupting the plan, which is important in a student project, where scope is prone to drift with new ideas coming up.
It provides an almost functional application at the end of the first two stages, so that the supervisor has something to examine well before the project is finished.
It can be integrated in a deferred way without being a hassle; it is a full increment that meets all the upstream expectations, so the model integration can be planned and resourced as an independent iteration without rework.
It fits easily into the build document, which is organized as a list of steps, in order, and including explicit verification steps.

1.6 Feasibility Study
Before the beginning of development, three feasibility dimensions were taken into consideration. Below is a summary of the conclusions for each dimension:
1.6.1 Technical Feasibility.
We have chosen all open source, well-documented, and supported technologies for Windows 10 and Windows 11. For over a decade, PyQt5 has been the choice of a cross-platform desktop GUI framework for Python. bcrypt, Matplotlib, and ReportLab are stable Python packages with large user bases, and the default zero-configuration desktop is SQLite.SQLAlchemy, the most popular ORM in the Python world, and SQLite, the default zero-configuration database for desktops, have stable Python bindings, while ReportLab has a large user base. The placeholder detection engine is implemented without Pillow; however, it is available on most Python distributions. The hardware requirement (a Windows machine with 4 GB RAM) is similar to office machines already being used at the target facility. No technical barriers are preventing the deployment, as all components used do not require a paid license or a network connection during normal use.
1.6.2 Economic Feasibility.
Personnel time is the predominant cost in the project. The hardware was pre-existing, the software is open source, and only the cost for SMTP service outbound alerts is needed, which can be the supervisor's pre-existing Gmail account for free. The detailed breakdown is given in Chapter 7. The figures indicate that the development cost is within the budget of the host organization to maintain a system that can be used in place of paper logs and to reduce the amount of time the supervisor spends each week preparing a summary by hand.
1.6.3 Operational Feasibility.
The same role hierarchy that currently exists at the facility is used in the application. Operators still make detection-time entries, supervisors still verify and approve, and administrators still manage users and settings. The interface employs Bengali-friendly Latin characters and a sidebar mode that is similar to that of familiar business applications, which makes it easy to pick up. A brief user guide and a session-based training program are enough to implement the system, and the rollback plan in case of failure is to go back to the current paper-based logs without losing any data. No operational dependency that will inhibit adoption.

Chapter 3.Requirement Engineering
3.1 Requirement Engineering
The job of requirement engineering is to get to know the system's needs, to document them in a format that can be used in system design, and to validate them with the people whose problems are being addressed. This chapter provides a brief overview of the four steps that led to the creation of SWMS, the methods of elicitation used to feed the inputs, the analysis used to group the raw input into themes, and the specification used to convert the themes into testable statements. The chapter ends with the use case diagram for the system. 
The requirement engineering activity of SWMS was performed in a sequence of three steps. For every step, an artefact was showcased to the practicum supervisor prior to the next step.
Elicitation: gather unprocessed information from the host organization, supervision, and literature review.
Analysis: Group the raw input into user, system, functional, and non-functional, and resolve any duplications and flag any conflicts.
Specification: list each requirement as a numbered testable statement; record the use case diagram.
3.2 Requirement Elicitation
The process of elicitation started with an unstructured interview with the host organization. The IT team lead and operations supervisor attended the session. The goal was to document the current process, the problems being faced, and the hopes they held for a digital solution to paper logs. This session generated approximately two pages of notes related to authentication, recordkeeping, alerts, and reporting. A second session was conducted a week later to confirm the recognition of the role hierarchy and discuss the procedure for confirming recognition of the detection results that the supervisor wished to keep manual for the first deployment. At the same time, the literature review brought up the typical non-functional issues of desktop applications in industrial environments; that of response time, password handling, error recovery, and offline operation. These were put on the elision backlog. Lastly, the practicum supervisor saw the backlog and suggested two more points from the project's academic side of the project: the need for CSV and Excel export for the data, and the organization of the codebase to be used for integration of the model in the next phase of the project.
3.3 Requirement Analysis
Themes were grouped from the raw input collected in the elicitation step as follows.
Security measures for authentication and access control. The system must recognize at each action who the operator is, must apply different permission sets to the three roles, and must ensure the security of the passwords at rest.
Detection and recordkeeping. Each detection event needs to be stored with the time of the detection, the operator that performed the detection, the resulting image, the categories detected, the confidence level, and the bin fullness indicator.
Verification. Supervisors will check pending detections and either approve or reject and can include comments. The verification status forms a part of the audit trail.
Alerts and notifications. Administrators set up rules using thresholds and periods. The system checks the rules after each detection and notifies by e-mail when it detects a violation of the rules.
Analytics and reporting. The Dashboard provides an overview of what has happened today. The report engine creates PDF reports on a daily, weekly, monthly, and custom range.
User management. Administrators add and edit operators and supervisors, and disable them. Self-deactivation isn't possible. 
Settings and audit. These can be set as SMTP, company name, and detection threshold. All critical actions add to an activity log, which can be queried later.
Operational quality. Long-running tasks should not block the user interface. Errors should be reported in a clear manner. The app should function offline for all purposes (except for sending emails).
Themes were discussed with the supervisor and were validated. These were used as the headings for the specification step to follow.

3.4.2. System Requirements
System requirements outline the modules of the application and the actions performed by each module. Here is a list of modules, ordered alphabetically and following the same order as the build document of the project.
Authentication and Session Handling
User launches the app and is presented with a login screen.
User types of their login name and password and click on the Login button.
The stored bcrypt hash for the username is retrieved and compared against the password entered.
If the match succeeds, the system updates the 'Last Logged In' date on that user and brings up the main app window.
On a failed match, the system shows an “Invalid credentials” message and keeps the user on the login screen.
The user's role (admin, supervisor, or operator) is loaded, and a check_permission helper is exposed that takes the hierarchy of admin, supervisor, and operator into account for all actions protected by the system.
When the user clicks on Logout in the sidebar, it will terminate the current session and log the user out of the computer.
User Management
Admin clicks on Users from the left side menu to open the user’s management screen.
Admin pushes the Add User button, enters username, full name, email, role, and initial password, and clicks Save.
The password is hashed in the system using bcrypt, the new user is added, and an entry is added to the activity log.
Admin clicks on a user and then Edit to update the user's name, emails, or role, then Save to save the change.
Admin chooses a user and clicks Deactivate to disable the account, which is not possible if the user selected to be deactivated is the currently logged-in admin.
Admin decides to reactivate the user and clicks Reactivate to restore access to the user.
One entry will be added to the activity log for every create, update, deactivate, and reactivate action.
Detection Execution
Click Detection in the left sidebar to launch the detection screen.
The operator clicks the Upload Image button and selects an image file from the local file system.
The system shows a preview of the image that is selected and allows the Run Detection button.
The operator clicks Run Detection; the detection engine runs in a background QThread, thus not freezing the UI.
The detection engine produces between one and four detections per of the seven configured waste categories with a confidence score ranging from 0.65 to 0.98 and a bin-fill level.
The system looks at a copy of the original image and can draw a bounding box around each detected object, saving the annotated image to the results directory.
A detection record is saved to the database, with the image path, annotated image path, operator ID, list of categories, confidence scores, fill level, status (Pending), and a time stamp.
It shows the annotated image and detection summary to the operator and logs the activity to the activity log.
Detection History and Export
To view the detection history screen, click on History on the left-hand side of the screen.
Records are loaded into a paginated table by the system, 25 rows per page.
The operator can only view their detection records, while supervisor/admins can view all records.
User clicks on filters by date range, category, status, or operator, and then clicks Apply to update the table.
By clicking any row, the user can see the original and annotated image side by side and detailed information about the detection.
On the currently selected list, the Supervisor/Admin clicks the Export CSV or Export Excel button to export the filtered list to disk.
An export activity entry is written to the activity log.
Detection Verification Workflow
Supervisor/Admin clicks on History and filters to Pending status.
User clicks the option to verify the detection or reject the detection as invalid.
User optionally types a note in the verification dialog and clicks Save.
The detection record is updated with the new status, verifier ID, verification timestamp, and note.
The system will record a verification record in the activity log.
Analytics and Dashboard
Click on Dashboard from the left-hand nav panel to view the analytics screen.
The system calculates and shows the total detections for today, the total detections in the system so far, the most frequent waste type, and the number of active alerts.
The system calculates and shows the distribution of categories and the distribution of the level of filling for the selected period.
The system calculates and displays the number of detections collected each day as a chart for the period of interest.
The system calculates and reports on operator performance metrics such as detections/operator and verification rate.
User updates the time period filter and changes all metrics and charts on the dashboard.
Report Generation
Supervisor/Admin clicks Reports on the left-hand side to display the Reports screen.
User chooses a period of time to generate a report (daily, weekly, monthly, or custom date range) and clicks Generate Report.
The report engine fetches and processes the detections for the selected period and executes in a QThread.
The system produces a category distribution plot using Matplotlib and includes it in a PDF.
The PDF contains summary statistics, a fill-level summary, and a paginated detection table for the defined time range.
The system saves the PDF in the reports folder and adds the file path, period, and generator ID to the reports table.
A report generation entry is written to the activity log, and the user clicks Open to display the report.
Alert Rule Management
Admin clicks on Alert Rules found on the left-hand side to view alert rules screen.
Admin enters Category, Threshold count, Period (hourly, daily, weekly), Notification e-mail, and active flag, and clicks Save.
The system adds the rule and records an addition to the activity log.
Admin clicks on the rule from the list and clicks Edit to edit any field, and then clicks Save.
Admin chooses a rule and clicks Delete to delete it; the system prompts for confirmation.
Admin switches the active flag for a rule on and off to enable or disable it, without deleting it.
Informal Assessment and Record of Learning.
Once a successful detection is made, the alert engine looks at all active rules and compares them to the detection counts for the rule's category and period as recorded.
If the threshold of the rule is exceeded, a new alert row is added to the system with the rule ID, the category, the number of breaches, the breach timestamp, and the status (unacknowledged).

A list of the acknower ID, the time, and date is recorded, and an activity log entry is written.

The service sends out the e-mail via smtplib over a secure connection.
The service notifies the alert engine of success or failure.

Activity Logging

The system takes the SQLite database file to a user-specified location and displays a toast message indicating success or failure.
User Interface Shell
It comes with a left sidebar and a stacked content widget on the right.
The navigation buttons (Dashboard, Detection, History, Reports, Alerts, Alert Rules, Users, Activity Log, Settings) are shown in the sidebar, based on the user's role.

Concurrency
All access to the database and to the file system is through a QThread, which is not the UI thread.
UI thread is responsive while detecting, Report generation, CSV / Excel, E-mail sending, and database backup.
The background threads send the signal when done, the UI thread receives the signal, and updates the appropriate screen.
In case of thread failure, an error toast appears on the UI thread, and results are recorded in the activity log.
Persistence
The first time it is run, it will generate a SQLite database file in the database/waste_management.db file.
The system generates all the necessary tables, including users, detection, report, alert, alert_rules, activity_log and settings.
The system automatically generates a default administrator account with a known initial password that should be changed once you log on as the admin for the first time.
The system default settings for applications (SMTP placeholders, company name, default confidence threshold).
Each write operation in the database is part of a transaction; failures are rolled back and reported as toast notifications.

Chapter 6.Project Planning and Scheduling
Project planning translates the requirement set into a sized estimate of the work and a schedule for delivering it. The function-point method was chosen for the size estimate because it is independent of the implementation language and produces a number that can be defended in front of a defense board. The schedule is presented as a Gantt chart at the end of the chapter.
6.1 Project planning and scheduling
The size estimate proceeds in five steps. First, the system's external functions are listed by type. Second, the complexity weights for each type are confirmed. Third, the unadjusted function point (UFP) contribution is calculated for each component type. Fourth, the technical degree of influence (TDI) is computed from the fourteen general system characteristics. Fifth, the value adjustment factor (VAF) and the adjusted function points (AFP) are derived from the UFP and the TDI.

Chapter 10.Ethical Consideration and Sustainability
10.1 Ethical Considerations
This chapter discusses the ethical considerations that shaped the design and construction of SWMS and the project's sustainability implications. The discussion is not abstract; each subsection refers back to a concrete design decision or feature in the application.
10.1.1. Data Privacy and Security
SWMS stores personal data (full names, email addresses, hashed passwords) and operational data (detection records linked to operators). The building follows three privacy principles. Passwords are stored only as bcrypt hashes; SMTP credentials are kept in the application settings table and are redacted before any value is written to the activity log; database backups are stored on the administrator's machine and are not transmitted off the device. The system runs offline by default, so there is no third-party server in the loop, and no data crosses the institution's perimeter without an explicit administrator action.
10.1.2. Intellectual Property
All third-party libraries used in the project are open source and licensed permissively (MIT, BSD, Apache 2.0, PSF, HPND). PyQt5 is dual licensed under GPL and a commercial license; the project's use is non-commercial and educational and falls within the GPL scope. The placeholder waste images used during testing were sourced from publicly licensed datasets and were not redistributed. The codebase does not include any copyrighted material from third parties.
10.1.3. User Impact
The system is intended to support operators, not to surveil them. The activity log records operational actions (a detection was run, a rule was created) and not biometric or location data. The verification workflow puts a supervisor in the loop before a record is treated as authoritative, which protects operators from being penalised for ambiguous detections. The role-based access control is strict by default: an operator only sees their own records on the history screen.
10.1.4. Bias and fairness
The placeholder detection engine assigns categories at random within a fixed distribution. The real model that will replace it must be evaluated for bias before deployment. Fairness in this context means the model should produce comparable accuracy across the seven configured waste categories rather than over-index on the categories that are over-represented in the training set. The integration plan in Chapter 11 includes a per-category accuracy report as a release criterion for the model.
10.1.5. Responsibility to Stakeholders
The project's stakeholders include the host organization, the operators, the recyclables purchasers, and the surrounding community. The build was reviewed with the host organization at every milestone. Operator feedback was solicited at the end of the UI Widgets phase and again at the end of the Polish phase. The Department of Environment guidelines on hazardous waste handling were consulted to ensure that the Hazardous category in the application is treated with the appropriate severity in the alert engine. 
10.1.6. Professional Responsibility
The work was carried out under the supervision of a faculty member at IUBAT. Source attributions are recorded in the references section. The codebase is structured for maintainability: layers are kept distinct, public methods are documented, and the build document records the full set of design decisions. If the project is handed over to another developer, the new owner can pick up the work without reverse-engineering it.
10.2 Sustainability Through Software Engineering
10.2.1. Economical Sustainability
SWMS replaces paper logs and manual spreadsheet preparation with a single application that runs on existing hardware. The recurring cost is bound: a small power draw on a desktop machine, an internet connection that is already paid for at the office, and the time the supervisor spends on the application instead of on manual reconciliation. The build itself uses only open-source components, so there is no license fee to renew. The economic case for the system rests on the time savings at the supervisor level and on the reduction of disputes with industrial buyers when the underlying data is structured and queryable.
10.2.2. Social Sustainability
The social case is two-fold. First, structured records of the volumes and categories of waste handled by the facility allow the host organization to make a stronger case to corporate clients who track diverted volumes for sustainability reporting. The clients, in turn, have a stronger case for the broader waste-diversion program, which is a small but real lever in the local context. Second, the system formalizes the role hierarchy in a way that makes the facility easier to audit, which improves working conditions for the operators by making promotions and pay raises traceable to recorded activity rather than to informal supervisor judgment alone 
Chapter 11.Conclusion
11.1 Conclusion
The Smart Waste Management System was designed and built to give a small recycling operation a structured digital record of its daily activity, a configurable alert engine that surfaces threshold breaches without manual checking, and a PDF report generator that the supervisor can run for any date range. The system was implemented in Python 3.10 with PyQt5 on a SQLite database accessed through SQLAlchemy. A placeholder detection engine produces realistic outputs so that every other part of the application can be developed and tested before the YOLOv8 model is introduced. Six representative test cases were executed against the build, and all passed against their expected results. The schedule was held within one day of the plan, and the cost stayed within the host organization's budget. The system is now ready for the next phase, which is the integration of the trained model and the addition of a live camera feed. 
11.2 Limitation
The following limitations apply to the build at the end of the practicum window:
Detection engine is a placeholder. The real model is not yet integrated. Confidence scores and category labels are randomly generated.
No live camera feed. The Start Camera button shows a placeholder message. Camera handling is deferred to the next phase, together with the model integration.
No scheduled reports. Reports are generated on demand. APScheduler integration for daily and weekly auto-generation is deferred.
No installer. The application is run from source via 'python main.py'. Packaging with PyInstaller is part of the polish work that follows the model integration.
Single-machine database. The SQLite file lives on the administrator's machine and is shared by manual copy if multiple machines need to read it. Multi-machine synchronization is out of scope.
English-only interface. Translations to Bengali are deferred to a later iteration.
11.3 Future Plan
The future plan addresses each limitation in turn:
Integrate the YOLOv8 model. Train on the TrashNet dataset augmented with locally collected images, and replace the detection_engine.py implementation behind the existing interface.
Add the live camera feed. Use OpenCV for capture, embed the preview in the detection screen, and run inference on a sliding window.
Add scheduled reports through APScheduler. Allow administrators to schedule daily, weekly, and monthly auto-generation with email delivery.
Package the application with PyInstaller for one-click installation on Windows.
Add a synchronisation layer over the SQLite file using a small server component that pushes change sets between machines on the local network.
Add a Bengali translation pass through Qt's translation files and a language selector on the settings screen.
The combined effort for the plan is estimated at twelve weeks of development plus four weeks of model training and validation, on top of the practicum window already completed.
